<!-- Prompt for the decryption stage on one sample whose code or strings are encrypted.
Replace {APP} with the work directory name. Also usable outside benchmarks. -->
You are a reverse engineer working statically on one Android sample. All paths are relative to the repository root, which is your working directory. The app is unpacked and scanned in work/{APP}/ (embedded payloads, if any, in work/{APP}.emb<k>/). Part of its code or configuration is encrypted: an encrypted payload in assets or resources, an encrypted string table, or both.

Goal: recover the plaintext statically and make it available for analysis.

1. Find the decryption. First read what the scripts already did, and do not redo it: triage.txt "Encrypted payloads decrypted by script" (payloads whose key is a constant; each is unpacked as work/{APP}.emb<k>/, and a child may hold the next encrypted layer) and "Files that look encrypted and were not decrypted" (the open ones, largest first); scan.txt "Encrypted strings decoded by script": string decoders that stringfog.py already decoded need no work (their plaintext is in jadx-strings/); one listed as undecodable is a lead. Leads: flows.txt lines marked "[XOR or cipher on the way]", the "Decoders and transforms" section of structure-leads.txt, callers of DexClassLoader/InMemoryDexClassLoader/loadDex, Cipher.getInstance, high-entropy files listed in triage.txt, "Embedded code found by content" and APKiD packer lines in triage.txt. Read the routine in work/{APP}/jadx/sources/ (or the embedded payload's sources), and find the key, IV, and algorithm (often a constant, a field set in a static initializer, a resource string, or derived from the package name or a certificate).
   When the routine is native (the Java side only loads a library and calls a native method, or native-summary.txt shows a library with a high-entropy section): decompile the JNI entry point and the functions it calls with ./cupella native-decompile.sh <lib.so> <function>, and follow the calls, not the names: a function named like a key derivation that the unpack path never calls is not part of it. Usual shapes: an outer library decrypts an inner library from its own data and loads it (decrypt the inner one first, write it to out/, and decompile that file the same way); keys and resource names are constants in .rodata, often loaded as 16-byte pieces and joined, so read the bytes at the addresses the code loads, in the order it stores them; a resource may be stored under an obfuscated path (apktool/res/values/ maps the resource name to the file; a file shadowed by another entry is under raw/_shadowing/); the loader may prepend bytes that the stored payload lacks (a dex without its first magic bytes). Check a cipher against its textbook form (RC4: a 256-entry table and swaps) before reimplementing it.
2. Reimplement it in Python as work/{APP}/decrypt/decrypt.py (only these standard-library modules: base64, binascii, struct, zlib, gzip, bz2, lzma, zipfile, io, os, sys, re, json, hashlib, hmac, codecs, string, shutil, collections, itertools, math, array; plus pycryptodome, which the image provides as `Cryptodome`: `from Cryptodome.Cipher import AES, DES, DES3, ARC4, Blowfish, ChaCha20`; subprocess is rejected, so there is no `openssl` command). It reads its input from ../raw/ (paths relative to work/{APP}/decrypt/, the working directory it runs in) and writes plaintext files to out/. Never change directory to the script's own location (`os.chdir(os.path.dirname(__file__))`): it runs from a read-only copy elsewhere. For string tables, write out/strings.txt with one "<where it is used>\t<plaintext>" line per string.
3. Run it only with: ./cupella run-decryptor.sh {APP}. That runs your script in the offline container and unpacks any decrypted dex or APK as work/{APP}.dec<k>/ with its own scan.txt, structure-leads.txt, flows.txt. Iterate until the output is valid (a dex starts with "dex\n", an APK with "PK"; strings are readable).
   - When decrypted dex files belong to an app whose manifest is elsewhere (the base of a split APK, a multidex payload), also write that app reassembled as one APK in out/ (its manifest, resources and assets plus all decrypted dex as classes.dex, classes2.dex, ...) and move the pieces to out/parts/: run-decryptor.sh lists parts/ but does not unpack it, so the app is analyzed as one sample with its manifest and one call graph.
   - When strings are decrypted by calls with constant arguments, also write out/string-map.tsv: one line per call, the call's string arguments in order and then the plaintext, tab-separated, with backslash, newline, tab and CR escaped as \\, \n, \t, \r. run-decryptor.sh then writes annotated copies of the jadx sources to work/<child>/jadx-strings/.
4. Write work/{APP}/decrypt/NOTES.md: algorithm, key and where it came from (path:line), inputs, outputs, and what could not be decrypted and why.

Progress: append one line to work/{APP}/decrypt/PROGRESS.md at each step, as you go, not at the end: "<step number> <what was done or found>" (routine found, key found, layer decrypted with output file and size, a dead end, the next step). Others read this file to follow the run.

Rules:
- Never run code from the app: no dex, no native library, no app script; only your own reimplementation, and only through ./cupella run-decryptor.sh. For bytecode jadx could not decompile, use ./cupella dex-disasm.py {APP} <Class[.method]>; for native code, use ./cupella native-summary.py, ./cupella native-disasm.py and ./cupella native-decompile.sh (they parse in the container); never parse APK files with host tools (readelf, objdump, cstool on the host). No other ./cupella commands, no network, never contact or look up any domain, address, or hash you find.
- Read only work/{APP}/, work/{APP}.emb*/ and work/{APP}.dec*/; write only under work/{APP}/decrypt/. Never read data/, bench/, reports/, or agent_docs/.
- If the key is not in the APK (fetched from a server, for example), stop and say so in NOTES.md; do not guess.

Reply with: decrypted (yes, partly, no), what was recovered, and the NOTES.md path.
