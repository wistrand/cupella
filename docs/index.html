Cupella

Static analysis of Android apps with a coding agent. Scripts unpack and scan the APK in an offline container. The agent reads the code behind the leads and writes a report. Each claim in it cites a file and line.

Read an example report Get started View on GitHub

app.apk (code, libraries, assets) → unpack, scan (offline container) → agent investigates (traces and decrypts) → reports/app.md (each claim cites file:line)

Output

One markdown report per APK: identity and signing, permissions and what uses them, components, network, data handling, native code, findings, indicators, open questions. Every finding cites a path and line under work/.

Example: a report on a loader APK around a native DDoS bot that finds its server through blockchain name records (snapshot from 2026-10-03).

Before a report counts as done, a script checks that every cited file exists, that the cited lines are in range, and that quoted text is on those lines; it does not check that the code supports the claim. That is the job of a second agent, which tries to refute each claim against the code. On one recent malware report it found 1 wrong and 6 overstated claims out of 47. All were fixed before the report was finished.

Some apps contain code for a feature they cannot use, for example because the permission it needs is never requested. The report says so, rather than listing it as something the app can do.

When to use it

Use Cupella for

  • Finding out what one malware sample does, with a file and line behind each claim and a list of indicators.
  • Packed or obfuscated apps: string encryption, encrypted payloads in assets, native decryption layers. They are decrypted statically.
  • A security review of one app, where each finding has to be checked against the code.
  • Comparing two versions of an app and reading the code behind each change.
  • Building up the method: when a step is missing, the agent adds it to a script, so the next APK gets it.

Use something else for

  • Scanning many apps, or a gate in CI: rule-based scanners such as MobSF and Quark-Engine take seconds per app without a model. Cupella takes minutes and many thousands of tokens per app.
  • A quick malicious-or-not verdict: a Cupella report describes behavior and gives no verdict. (The MalEval benchmark prompt asks the agent for one; that is where the malware-flagged numbers below come from.)
  • Behavior that only shows at run time: keys made at run time, code or configuration fetched from a server. That needs dynamic analysis.
  • Code you may not send to a hosted model: the agent reads excerpts of the decompiled code.
  • iOS or other formats: only the Android front end exists.

How it works

data/app.apk
  ./cupella unpack.sh    extract (size limits, no symlinks), apktool, jadx, manifest,
                     signatures, native and Flutter summaries, embedded payloads
  ./cupella scan.sh      decoded strings, pattern sections, call-graph and data-flow
                     leads, missing permissions and libraries, family markers
  agent              reads the code behind the leads
  decryptor agent    if code is encrypted: writes decrypt.py, linted, run locked
                     down; decrypted payloads are unpacked and scanned as samples
  agent              writes reports/app.md; cite-check and a verifier agent check it

Anti-analysis

Handled so far, each reported as a finding:

  • ZIP tricks: fake encryption flags, entries that shadow real files, path tricks, symlink entries, decompression bombs.
  • Junk bytes inserted to make the usual decompilers fail. Cupella's own disassembler reads past them.
  • Manifests padded with hundreds of invented permissions.
  • String encryption at every call site. Common schemes decode automatically; the plaintext is written next to each call.
  • Payloads encrypted in assets, in several layers. One banking-trojan dropper had five; all were decrypted with keys found in the APK.
  • App code hidden in a package that looks like a common library.
  • Stripped native libraries that standard tools cannot read.

Results

Public benchmarks, static only, scored blind by a separate model. MobSF and Quark-Engine ran on the same apps and were scored the same way. The three tools do different jobs: MobSF reports weaknesses and permissions, Quark-Engine matches rules for malicious behavior and answers in about 2 seconds without a model, and Cupella is an agent that reads the code over minutes.

Deliberately vulnerable apps (InsecureBankv2, OVAA, InsecureShop, AndroGoat): 85 of 89 listed vulnerabilities found. MalEval samples with encrypted code: behavior recall 50% before decryption, 66% after.

Quark-Engine was also tested as a lead source for Cupella. Limited to an app's own code, it raised nothing on the 5 harmless apps and found 5 pieces of code that Cupella's own leads had missed. Its results are now part of Cupella's scan.

Caveats:

  • Quark-Engine looks for malware behavior and has no rules for vulnerabilities, so it was not scored on Ghera. It crashed on 2 of the 25 MalEval apps, which are built to break tools; those count as nothing found.
  • Each tool's MalEval output was sorted into behavior categories by a model, and every agent result was scored by a model.
  • The MalEval set is small: 25 apps.
  • The Ghera result is from a second run, after the instructions were improved using the first run's misses, so it is somewhat optimistic. No separate test set exists yet.
  • The vulnerable test apps are well known, so a model may partly remember them.
  • Cost: the scanners take seconds per app. Cupella takes minutes and, for a full analysis of a real app, hundreds of thousands of tokens.

Safety

Where the data goes

  • In the container, on your machine, offline: unpacking, decompiling, scanning, and running decryptors. Nothing here reaches a network.
  • On your machine, outside the container: the coding agent. It reads the scripts' output under work/: decompiled code, decoded strings, and summaries of the sample.
  • At your model provider: whatever the agent reads is sent to the model behind it, including excerpts of the decompiled code. Do not analyze code you may not send to that provider. A harness running a local model would keep it on your machine, but no local-model harness has been tested with Cupella.

Protections

  • Samples are parsed only in a container with no network, no capabilities and a read-only root, under memory, process, file-size and time limits.
  • Extraction refuses entries that would land outside the sample's directory, symlink entries and decompression bombs. ./cupella setup tests this before first use.
  • Agent-written decryptors run in a container with no network and only their output directory writable; that container is the boundary. A lint (no exec, no subprocess, no network modules) is a best-effort filter in front of it, not a sandbox.
  • Helper agents that read text from a sample get no shell, or one limited to a few listed commands. That limit is an instruction, not something the coding tools enforce, and Claude Code's permission rules can be sidestepped by writing a command differently.
  • The agent itself reads sample-derived text on the host: for live malware, run the harness session in a VM or under a dedicated user account.
  • Text in a sample that addresses the agent goes into the report as a finding. Names and addresses from a sample are never contacted.

Setup

Requires Docker and a coding agent that reads AGENTS.md and runs shell commands.

git clone https://github.com/wistrand/cupella.git cupella && cd cupella
./cupella setup   # checks Docker, builds the image once, self-test
cp ~/Downloads/some.apk data/
claude            # or another coding agent, started here

Then ask it to analyze data/some.apk. A separate workspace keeps cases out of the checkout:

./cupella setup --workspace ~/cases/acme  # own data/, work/, reports/; read-only copies of the docs
cd ~/cases/acme

Harnesses

Instructions are in AGENTS.md, subagent roles in roles/. Claude Code gets generated agent types and permission rules, and ran all benchmarks and subagent stages. Codex and Antigravity have also run analyses successfully. Gemini CLI and Cursor have setup notes and are untested.

Benchmarks

./bench-setup fetches Ghera, MalEval and the vulnerable apps and checks them against recorded hashes. It asks before downloading MalEval, which is live malware. ./cupella gate measures how well the scripts point at known findings, before and after a script change, and fails if anything gets worse.

Limits

  • Static only: keys made at run time, code fetched from a server and server-side configuration are out of reach.
  • Minutes per app, more for packed malware. Too slow for a CI gate.
  • Results vary a little between runs of the same benchmark.
  • Android only. A new format needs its own front end and benchmark.
  • Prompt injection: sample text is scanned for instructions aimed at the agent and treated as data. A new trick can still get through.
  • The model provider's safety filter sometimes stops an agent partway through reading malware. Its notes are kept, but that part may need a second pass.
