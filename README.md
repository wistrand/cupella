# Cupella

A workspace for static analysis of Android APKs with a coding agent.
Project site: [wistrand.github.io/cupella](https://wistrand.github.io/cupella/).

Drop an APK into `data/`, ask the agent to analyze it, and get a markdown report in
`reports/`: what the app is, what it requests, which libraries and endpoints it
contains, how it is signed, and anything that looks odd. The agent unpacks and
decompiles the APK with jadx and apktool, then reads the result. Nothing from the APK
is executed or installed.

## Requirements

- Docker, with the current user allowed to run containers.
- A coding agent that reads `AGENTS.md` and can run shell commands, started in this
  directory. Claude Code ran the benchmarks and the subagent stages and gets agent types
  generated by `./cupella setup`; Codex and Antigravity have also run analyses
  successfully. Setup for other harnesses is in `agent_docs/harnesses.md`.
- About 3 GB for the image, more for `work/` (a large app unpacks to a few GB).
- Python 3 on the host (standard library only) for the gate, `./cupella check`, and the
  benchmarks; analysing samples does not need it.

## Quick start

```bash
git clone <this repository> cupella && cd cupella
./cupella setup   # checks Docker, builds the image once, self-test
cp ~/Downloads/some.apk data/
claude            # or your coding agent, started in the checkout
```

To keep your cases out of the checkout, make a workspace and work there instead:

```bash
./cupella setup --workspace ~/cases/acme  # own data/, work/, reports/; read-only copies of the docs
cd ~/cases/acme && claude                 # or your coding agent
```

A workspace holds read-only copies of the agent docs and a `./cupella` wrapper that
runs the checkout; nothing else of the checkout is reachable from it.

- Updating: `git pull` in the checkout. The next `./cupella` run in a workspace
  refreshes its copies; `./cupella sync` does it at once and restores copies edited by
  hand.
- Moving the checkout: rerun `<checkout>/cupella setup --workspace <dir>`.
- Improvements: an agent in a workspace does not edit scripts or docs. It writes
  proposals to the workspace's `proposals/`, and can try a proposed extraction on the
  sample as code (`./cupella try-proposal <slug> <name>`, linted and offline like a
  decryptor); you apply them in the checkout, where `./cupella gate` runs (a fork is
  the way to share them). `./cupella proposals` in the checkout lists the open ones
  across your workspaces, and `./cupella proposals set <workspace> <slug> applied`
  (or `rejected`) records what you decided.
- `./cupella workspaces` in the checkout lists the workspaces made from it, with their
  sample, report, and open-proposal counts. A workspace made before this list existed
  appears after its next `./cupella` run, or with `./cupella workspaces --find <dir>`.
- Git: setup writes a `.gitignore` once, if none exists, so a workspace kept in git
  tracks `reports/` and `proposals/` but never the samples, `work/`, or generated files.
- Deleting: the doc copies are read-only, so use `chmod -R u+w <dir> && rm -rf <dir>`.

`./cupella help` lists the commands and scripts.

Then ask the agent, for example:

- "analyze data/some.apk"
- "analyze data/some.apk on a budget" (fewer subagents and a shorter check, for small
  token limits; the report says what was left out)
- "which network endpoints does data/some.apk talk to?"
- "compare the permissions of data/a.apk and data/b.apk"

## Layout

| Path       | Contents                                             |
|------------|------------------------------------------------------|
| `data/`    | APKs to analyze (benchmark sets in subdirectories)   |
| `reports/` | one report per APK                                   |
| `work/`    | unpacked and decompiled output, safe to delete       |
| `cache/`   | build cache for the Dart analysis tool               |
| `scripts/` | unpack, scan, lead, and benchmark scripts            |
| `prompts/` | prompt templates for subagent stages and benchmarks  |
| `roles/`   | subagent roles (what each may read, write, and run)  |
| `host/`    | host-side helpers run by `./cupella` (the benchmark gate, the regression check) |
| `bench/`   | benchmark data, fetched by `./bench-setup` (not in the repository) |
| `bench-sources/` | where each benchmark file comes from, and its hash |
| `agent_docs/` | runbooks, report format, traps, benchmarks, further work |
| `docs/` | project site ([wistrand.github.io/cupella](https://wistrand.github.io/cupella/)); `docs/examples/` holds an example report |

Signatures are verified during unpacking. The scripts also run on their own:

```bash
./cupella unpack.sh data/some.apk     # unpack, decode, decompile; writes work/some/triage.txt
./cupella scan.sh some                # pattern searches; writes work/some/scan.txt
./cupella native-disasm.py work/some/raw/lib/arm64-v8a/libfoo.so --jni   # annotated native disassembly
```

Native libraries are summarized automatically (`work/some/native-summary.txt`), known
trackers and packers are identified (`trackers.txt`, `apkid.txt`), and Flutter and
React Native apps get their compiled Dart or JavaScript code made readable. Two
versions of an app can be compared with `./cupella apk-diff.py <old> <new>`, and
`./cupella lead-eval.py <name>` checks which leads pointed at a finished report's findings.
Experimental, off by default: a local model served by
[llav](https://wistrand.github.io/llav/) can rank functions into a reading list
(`./cupella model-leads.py <name>`). No script runs it unless you do, and it has not
found anything the rest missed.

Everything runs in a container. The image contains jadx, apktool, Ghidra, blutter, APKiD,
hermes-dec, and Quark-Engine (with androguard) at pinned versions (full list:
[agent_docs/reference.md](agent_docs/reference.md#third-party-tools)); the analysed files are parsed with no network access and with only
`work/` writable. Two steps use the network and say so: comparing libraries against
official builds (`./cupella reference-check.py`), and the build of the Dart analysis tool
the first time a Flutter app with a new Dart version is analysed. That build happens
automatically, takes several minutes, and runs in a container that cannot see the APK.

## Safety

The agent runs on the host. The APK does not: it is parsed only inside the container,
which has no network, no capabilities, a read-only root, and write access to `work/`
alone. Nothing from an APK is executed, installed, or loaded, and no address found in
one is contacted. Archive entries cannot land outside the sample's directory: `../` and
absolute names are rejected, symlink entries are removed after extraction, and the
build cache that later runs execute is read-only to every container that sees an APK
(`./cupella fixtures/zipslip-test.sh` checks the extraction side).

Some steps need code the agent writes, such as reimplementing a payload's decryption.
That code runs in a container with no network that can write only that sample's
`decrypt/` directory; that container is the boundary. Before it runs, a lint rejects
exec, eval, dynamic imports, subprocess, network modules, and modules outside the
standard library's byte, file, and format modules and pycryptodome. The lint is a
best-effort filter on agent-written code, not a sandbox.

Subagents that read APK content have no shell (role `reader`) or a shell limited to
`./cupella run-decryptor.sh`, `./cupella dex-disasm.py`, and the native scripts (role
`decryptor`). Claude Code enforces the tool lists of both roles; it does not restrict
which commands a decryptor's shell runs, and neither does any other harness so far, so
that list holds by instruction only. The host-side rules in `.claude/settings.json`
(allow `./cupella`, deny `adb`, `readelf`, `unzip`, and other parsing tools) are prefix
matches: a full path or `bash -c` gets around them. Text in an APK that addresses the
agent is reported as a finding, never followed.

For live malware: keep samples under `data/malware/` (gitignored with the rest of
`data/`), keep the file names as they are (letters, digits, `.`, `_`, `-`), and expect
reports to contain keys, command names, and indicators in clear text. The agent reads
sample-derived text on the host, so run the harness session itself in a VM or under a
dedicated user account.

## How it works

Scripted tools and agent runs each do the part they are good at. The scripts do the
repeatable extraction: unpacking, decoding the manifest and resources with apktool,
decompiling with jadx, summarizing permissions, exported components and native
libraries, running a fixed set of pattern searches, and finding functions by their
place in the call graph (entry points and what they reach, dispatch tables, loops,
decoders). The agent then reads the code behind each lead, works
out what it does and whether it is on by default, and writes the report with evidence
for every claim. What an agent run learns goes back into the scripts, so each analysis
makes the next one better (from a workspace, through `proposals/`).

Malformed APKs (fake ZIP encryption, tampered manifests) are read the way Android
reads them. Payloads hidden in assets under misleading names are found by content and
analyzed as samples of their own.

For a full analysis the agent unpacks and scans, reads the leads, decrypts hidden
payloads when it has to, writes the report, then has a fresh agent try to refute every
claim before the citations are checked mechanically. The order of work is in
`agent_docs/workflow.md`.

Reports go to `reports/`, which is not part of the repository. One example is:
[docs/examples/23282313-ddos-bot-loader.md](docs/examples/23282313-ddos-bot-loader.md)
([rendered on the site](https://wistrand.github.io/cupella/report.html?f=23282313-ddos-bot-loader.md)),
a loader APK around a native DDoS bot that finds its server through blockchain name
records (a snapshot from 2026-10-03; the signer's name is redacted).

## How well it works

Agent runs on public benchmarks, static only, scored by a separate model:

| Benchmark | Result |
|-----------|--------|
| Ghera, 59 vulnerable/fixed app pairs, blind, with verification | 55 of 59 vulnerabilities found; 6 fixed apps also flagged |
| InsecureBankv2, OVAA, InsecureShop, AndroGoat | 85 of 89 listed vulnerabilities found |
| MalEval, 20 malware families and 5 benign apps | 19 of 20 malware and 5 of 5 benign classified right; behaviors 65% recall, 70% precision |
| MalEval, the 6 samples with encrypted code, after static decryption | behaviors 50% -> 66% recall, 68% -> 74% precision |

On the same apps, scored the same way: MobSF 4.5.3 found 20 of 59 Ghera
vulnerabilities (6 fixed apps flagged too); Quark-Engine was not scored on Ghera, since
it has rules for malware behavior and none for vulnerabilities. On the MalEval slice
their findings support 19% and 26% behavior recall, against 65% here; Quark-Engine
crashed on 2 of the 25 samples (ZIP entries marked encrypted). Both take seconds per
app without a model. The agent takes minutes, and a full analysis of a real app
hundreds of thousands to over a million tokens: in Claude Code runs on 2026-10-03, the
subagents used about 0.3M tokens on a small bot loader and about 1.4M on a two-stage
banking RAT (six readers, a verifier); one reader on one area used 100k to 265k tokens
(4 to 7 minutes) and verifying one report 125k to 280k (3 to 10 minutes). The main
agent's own use is not counted. Budget table: `agent_docs/workflow.md`.

Caveats: the runbook's vulnerability checklist was written from Ghera's own misses, so
the Ghera result is optimistic (a held-out set is open work); the vulnerable apps are
well known, so some recall from training is possible; every agent benchmark is scored by a model,
not a person, and most benchmarks ran once or twice.
Encrypted payloads are decrypted statically by an agent-written decryptor that is
linted and run in a locked-down container; what is still missed is mostly code
behind native decryption layers.

Details, caveats, and how to rerun: `agent_docs/benchmarks.md`. Known gaps and next
steps: `agent_docs/further-work.md`.
